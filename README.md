# Chapters

#### Video Demo: [https://youtu.be/O9azYuJ_VJw](https://youtu.be/O9azYuJ_VJw)

#### Description:

Chapters is a gamified reading web application built as my final project for CS50x. The idea behind it is simple: reading is good for you, but it's easy to let it slip when there's no immediate feedback loop pulling you back to a book. Chapters tries to fix that by wrapping the actual act of reading a PDF in the same kind of progression systems that make video games so sticky — experience points, levels, streaks, quests, and coins — so that opening a book and making progress in it feels rewarding in a very tangible, visible way.

At its core, Chapters is a Flask application backed by a PostgreSQL database, with every query written in raw SQL through psycopg2 rather than through an ORM like SQLAlchemy. This was a deliberate choice. I wanted to actually understand what was happening at the database level — how joins, transactions, and schema design decisions ripple through an application — rather than let an abstraction layer make those decisions invisible to me. It made early development slower, but it meant that when something went wrong (and plenty went wrong), I could reason about it directly instead of debugging through a layer of generated SQL I hadn't written myself.

**Authentication.** Users can sign up and log in with a username and password. Passwords are never stored in plaintext; they're hashed using Werkzeug's password hashing utilities before being written to the database, and verified the same way on login. Sessions are used to keep users logged in across requests.

**Book uploads and storage.** Once logged in, a user can upload PDF files, which are stored on disk under `uploads/<user_id>/` so that each user's library is kept separate, while metadata about each book (title, filename, upload date, reading progress, etc.) lives in the database. This split between filesystem storage for the actual file and database storage for metadata keeps the database lean and avoids storing large binary blobs in PostgreSQL.

**The reader itself** is the most technically involved part of the project. It's built on top of Mozilla's pdf.js library and renders pages onto an HTML canvas rather than relying on the browser's native PDF viewer, which gave me full control over the reading experience. On top of the canvas sits an invisible text layer, positioned exactly over the rendered glyphs, which is what allows users to select and copy text even though what they're actually looking at is a bitmap image. Getting this text layer to line up correctly with the canvas turned out to be one of the trickier parts of the project — pdf.js relies on a `--scale-factor` CSS variable to compute where each span of text should sit, and if that variable isn't set correctly the text layer drifts out of alignment with the visible page. I also ran into a more subtle bug where `user-select: none` on the page container (needed so that dragging to pan the page didn't accidentally start a text selection) was silently blocking selection everywhere, including on the text layer itself — the fix was to explicitly re-enable `user-select: text` on the text layer specifically, so panning and text selection could coexist. Beyond that, the reader includes a lazy-loading thumbnail sidebar (using an `IntersectionObserver` so thumbnails only render as they scroll into view, rather than rendering every page of a 400-page book up front), in-document search, zoom, fullscreen support, and a collapsible reading timer. Pages are rendered at a minimum of 2x supersampling relative to the device's pixel ratio, capped at a 4096px longest side, which keeps text sharp on high-DPI screens without producing unreasonably large canvases on longer documents.

**The gamification layer** is what ties the whole project together. Every second a user spends reading is tracked and converted into XP, which pushes them up a leveling curve where each level requires twice as much XP as the one before it, starting from a base of 100 XP for level one. This doubling curve was chosen over a linear one because it keeps early levels quick and satisfying while still giving long-term users a meaningful long-term goal, mirroring the leveling curves in many games I enjoy. Alongside XP, users earn coins and can complete quests (for example, reading for a certain number of minutes in a day), and the app tracks daily reading streaks to encourage consistency. A leaderboard lets users see how their reading compares to others. One of the trickier bugs I ran into here was entirely a wiring problem rather than a logic problem: the function that awards XP and updates quest progress has to be explicitly called from every route that represents reading progress, and it's very easy to add a new route and simply forget to call it — resulting in a page that looks like it's tracking reading time but silently never gives XP. Once I noticed this, I made a habit of checking every reading-related route by hand to confirm the hook was actually wired in.

On the schema side, reading time is stored in seconds (`seconds_today` and `seconds_spent`) rather than minutes, which gives much finer-grained tracking and avoids rounding errors accumulating over many short reading sessions. I also keep two separate timestamp fields: `last_read_date`, a plain date used for streak calculations, and `last_opened_at`, a full timestamp used to determine which book a user most recently opened — these serve genuinely different purposes and conflating them into one field early on caused streaks and "continue reading" behavior to interfere with each other.

Overall, Chapters brought together everything from raw SQL and authentication to canvas rendering and UI/UX design decisions around motivation and habit formation, and it's the project I'm most proud of from this course.
